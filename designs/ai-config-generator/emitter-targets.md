# `ai-config-generator` — emitter target reference

Per-target field-mapping table and concrete output examples. This is the operational spec each emitter implementation must follow.

## Target matrix at a glance

| Target | Output paths | Frontmatter? | Per-skill files? | MCP file? | Cloud variant |
|---|---|---|---|---|---|
| **claude** | `.claude/rules/*.md`, `.claude/skills/*/SKILL.md`, `.claude/agents/*.md`, `CLAUDE.md`, `.mcp.json` | yes (Claude schema) | yes (folder per skill) | yes — `.mcp.json` | n/a (Claude is local) |
| **codex** | `AGENTS.md` | no (markdown only) | inlined as sections | documentation-only section | `codex-cloud` (cloud_mode=true) |
| **copilot** | `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md`, `.github/copilot-mcp.recommended.md` | yes (`applyTo`) | yes (one .instructions.md per skill with globs) | **none** — Coding Agent MCP is configured in repo Settings UI, not a committed file. Generator emits `copilot-mcp.recommended.md` advisory instead | `copilot-coding-agent` (cloud_mode=true) |
| **gemini** | `GEMINI.md` | no | inlined as sections | documentation-only section | n/a (Gemini Code Assist runs in IDE) |
| **cursor** | `.cursor/rules/*.mdc`, `.cursor/mcp.json` | yes (`description`, `globs`, `alwaysApply`) | yes (one .mdc per skill) | yes — `.cursor/mcp.json` | `cursor-bg-agent` (cloud_mode=true) |
| **windsurf** | `.windsurf/rules/*.md` | yes (`trigger`, `globs`, `description`) | yes | not yet covered (revisit when Windsurf MCP is mature) | n/a yet |

`cloud_mode: true` means MCP servers without `runs_in.<cloud-target>: true` are silently dropped, and inline-audience blocks not visible to the cloud target are stripped.

## Claude emitter

### Output paths

```
<repo>/CLAUDE.md
<repo>/.claude/rules/<name>.md
<repo>/.claude/skills/<name>/SKILL.md
<repo>/.claude/agents/<name>.md
<repo>/.mcp.json
```

### CLAUDE.md template

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->

# {{ repo_display_name }}

Repo-level guidance for Claude Code in `{{ repo_name }}`.

## Rules

{{ for rule in rules where audience.includes('claude') }}
- [`{{ rule.name }}`](.claude/rules/{{ rule.name }}.md) — {{ rule.description }}
{{ end }}

## Skills

{{ for skill in skills where audience.includes('claude') }}
- **{{ skill.name }}** — {{ skill.description }}
{{ end }}

## ContextStream / MCP

See `.mcp.json` for the configured server list.
```

### Rule file → `.claude/rules/<name>.md`

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->
---
name: {{ rule.name }}
description: {{ rule.description }}
priority: {{ rule.priority }}
{{ if rule.applies_to.any }}
applies_to:
{{ for glob in rule.applies_to }}
  - "{{ glob }}"
{{ end }}
{{ end }}
---

{{ rule.body_filtered_for_claude }}
```

### Skill file → `.claude/skills/<name>/SKILL.md`

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->
---
name: {{ skill.name }}
description: {{ skill.trigger.description }}
---

{{ skill.body_filtered_for_claude }}
```

If a skill has attachments (any non-`SKILL.md` file in `mrploch-development/.claude/skills/<name>/`), they are copied alongside `SKILL.md` byte-for-byte. The header comment is **not** prepended to attachments — they're treated as opaque payloads.

### `.mcp.json`

Generated from `mcp-servers.yaml` filtered by `runs_in.claude: true`:

```json
{
  "_generator": "ai-config-generator",
  "mcpServers": {
    "{{ server.id }}": {
      "command": "{{ server.command[0] }}",
      "args": {{ server.command[1..] | json }},
      "env": {{ server.env | json }},
      "transport": "{{ server.transport }}"
    }
    // … one entry per claude-eligible server
  }
}
```

JSON keys are sorted alphabetically for determinism.

## Rules

{{ for rule in rules where audience.includes('codex') sorted by priority desc, name asc }}
### {{ rule.title_or_humanised_name }}

{{ rule.description }}

{{ rule.body_filtered_for_codex }}

{{ end }}

## Skills

{{ for skill in skills where audience.includes('codex') sorted by name asc }}
### Skill: {{ skill.title_or_humanised_name }}

**When to use:** {{ skill.trigger.description }}

{{ if skill.applies_to.any }}
**Applies to:** {{ skill.applies_to | join(', ') }}
{{ end }}

{{ skill.body_filtered_for_codex }}

{{ end }}

## Available MCP tools

{{ if not cloud_mode }}
The following MCP servers are configured for local Codex CLI runs (`~/.codex/config.toml`):

{{ for server in mcp_servers where runs_in.codex_cli sorted by id asc }}
- **{{ server.id }}** — {{ server.description }}
{{ end }}
{{ end }}

{{ if cloud_mode }}
**Note:** Codex Cloud does not currently support MCP. The tools above are available only when working locally with Codex CLI.
{{ end }}
```

### Cloud variant differences

`codex-cloud` (set `cloud_mode: true` in `targets.yaml`):

- Inline-audience blocks must include `cloud-safe` *or* `codex-cloud-only` to be emitted.
- The "Available MCP tools" section reverts to the cloud-mode variant above (informational only).
- Any skill whose body contains `mcp__contextstream__*` references is replaced with a stub: *"This skill is not available in Codex Cloud — see `.ai-context/` for the snapshot fallback."* (assuming snapshot export is enabled for the repo).

### Nested AGENTS.md

`emit_nested_agents_md_for_globs: true` (off by default — phase 4 candidate) lets a rule with `applies_to: ["tests/**"]` emit into `<repo>/tests/AGENTS.md` instead of (or in addition to) the root `AGENTS.md`. Codex walks up from the file being edited, so nested files override.

## Copilot emitter (`copilot` and `copilot-coding-agent`)

### Output paths

```
<repo>/.github/copilot-instructions.md
<repo>/.github/instructions/<name>.instructions.md
<repo>/.github/copilot/mcp.json    (cloud variant only, if MCP enabled)
```

### `.github/copilot-instructions.md`

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->

# Copilot Repository Instructions — {{ repo_display_name }}

{{ for rule in rules where audience.includes('copilot') and rule.applies_to.empty sorted by priority desc, name asc }}
## {{ rule.title_or_humanised_name }}

{{ rule.body_filtered_for_copilot }}

{{ end }}
```

Rules with `applies_to` globs are emitted as separate `.instructions.md` files. Repository-wide instructions go in `copilot-instructions.md`.

### `.github/instructions/<name>.instructions.md`

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->
---
applyTo: "{{ rule.applies_to | join(',') }}"
---

# {{ rule.title_or_humanised_name }}

{{ rule.body_filtered_for_copilot }}
```

`applyTo` takes a single string; the emitter joins multiple globs with commas. Empty `applies_to` ⇒ rule goes in `copilot-instructions.md` instead.

### Skill mapping

Each skill with audience `copilot` becomes a `.instructions.md` file:

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->
---
applyTo: "{{ skill.applies_to | join(',') if any else '**' }}"
---

# {{ skill.title_or_humanised_name }}

**When to use:** {{ skill.trigger.description }}

{{ skill.body_filtered_for_copilot }}
```

### `.github/copilot-mcp.recommended.md` (advisory)

GitHub Copilot Coding Agent does **not** read MCP server configuration from a committed file. MCP servers are configured per-repo via the GitHub Settings UI (Settings → Copilot → Cloud agent → MCP configuration). The generator therefore emits an **advisory file** the maintainer can paste from:

```markdown
<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->
# Copilot Coding Agent — recommended MCP servers

These servers are cloud-safe and OAuth-free. Paste each block into
**Settings → Copilot → Cloud agent → MCP configuration** in this repository.

## github
```json
{ "type": "http", "url": "https://api.githubcopilot.com/mcp", ... }
```

## context7
```json
{ "type": "http", "url": "https://mcp.context7.com/mcp", ... }
```

...
```

The list is filtered by:
- `runs_in.copilot-coding-agent: true`
- `auth ≠ oauth` (V12 hard validator — Coding Agent does not support OAuth-authenticated MCP)
- All env-var names matching `COPILOT_MCP_*` (V13 hard validator)

Stdio servers with `runs_in.copilot-coding-agent: true` are allowed (Copilot Coding Agent supports stdio transport in its sandbox), but the generator warns when one is included so the maintainer can confirm the binary is installable in the agent's runner image.

## Cursor emitter (`cursor` and `cursor-bg-agent`)

### Output paths

```
<repo>/.cursor/rules/<name>.mdc
<repo>/.cursor/mcp.json
[<repo>/.cursorrules     ← legacy redirect, opt-in only]
```

### Rule file → `.cursor/rules/<name>.mdc`

```markdown
---
description: {{ rule.description }}
{{ if rule.front_matter_extras.cursor.alwaysApply or rule.priority == 'critical' }}
alwaysApply: true
{{ end }}
{{ if rule.applies_to.any or rule.front_matter_extras.cursor.globs }}
globs:
{{ for glob in rule.applies_to ?? rule.front_matter_extras.cursor.globs }}
  - "{{ glob }}"
{{ end }}
{{ end }}
---

<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->

{{ rule.body_filtered_for_cursor }}
```

Note: in `.mdc`, the generator-comment goes **after** the closing `---` because Cursor's frontmatter parser is strict.

### Skill mapping

Each skill becomes one `.mdc` file with the trigger info translated:

- `description` ← `skill.trigger.description`
- `globs` ← `skill.trigger.globs ?? skill.applies_to`
- `alwaysApply: true` if no globs (so the skill body is always loaded; the user / agent decides when to act on it)

### Legacy `.cursorrules`

If `targets.yaml > cursor.output.legacy_cursorrules: true`, a one-line redirect is emitted:

```
# This file is replaced by .cursor/rules/*.mdc — see https://docs.cursor.com/...
```

Default off. Cursor has been deprecating `.cursorrules` for a while.

## Windsurf emitter

### Output paths

```
<repo>/.windsurf/rules/<name>.md
```

### Rule file

```markdown
---
trigger: {{ rule.front_matter_extras.windsurf.trigger ?? '<computed-from-priority-and-globs>' }}
description: {{ rule.description }}
{{ if rule.applies_to.any }}
globs:
{{ for glob in rule.applies_to }}
  - "{{ glob }}"
{{ end }}
{{ end }}
---

<!-- generated by ai-config-generator from mrploch-development/.claude/ — do not edit -->

{{ rule.body_filtered_for_windsurf }}
```

`trigger` values (confirmed): `always_on`, `model_decision`, `glob`, `manual`. Map from priority + globs:

- priority `critical` ⇒ `always_on`
- globs present ⇒ `glob` (regardless of priority — needs `globs` field populated)
- priority `high` or `normal` and no globs ⇒ `model_decision`
- priority `low` or no description ⇒ `manual`

Per-file character limit: 12,000. Generator warns when a body approaches 10,000 chars; hard-fails at 12,000.

See [`cloud-agents.md`](cloud-agents.md) — Windsurf section — for source citation.

## Body filtering rules

`body_filtered_for_<target>` performs three transforms in order:

1. **Strip inline-audience blocks** that don't include the current target.
2. **Replace cross-references** to other rule/skill names with target-specific links:
   - For Claude: `[name](.claude/rules/name.md)` or `[skill: name]` for skills
   - For Codex/Gemini: `[#section-anchor](#name)` (anchored within the same file)
   - For Copilot: `[name](.github/instructions/name.instructions.md)` for instructions, otherwise inline name
   - For Cursor: `[name](.cursor/rules/name.mdc)`
   - For Windsurf: `[name](.windsurf/rules/name.md)`
3. **Rewrite Claude-specific tool invocations** (`mcp__contextstream__*`, `Skill(...)`, `Agent(...)`) when the target is non-Claude:
   - If the surrounding block is `audience: claude-only`, it's already gone — no-op.
   - If the block is `audience: cross-tool` but mentions a Claude tool by name, the emitter logs a `body-rewrite-required` diagnostic and falls back to a generic phrasing if a `body_overrides.<target>` field is provided in frontmatter.
   - If no override is provided, the rule's body is included verbatim with a `<!-- note: contains Claude-specific tool references; non-Claude targets should adapt -->` warning at the top. Logged as a diagnostic.

The third transform is conservative because over-aggressive auto-rewriting risks silently changing meaning. Body overrides keep the human in the loop.

## Body overrides

For high-value rules where the same intent is expressed differently per target, the canonical entry can carry per-target body overrides:

```yaml
---
name: pr-checks-completion-gate
audience: [cross-tool]
body_overrides:
  claude: |
    Use `gh pr checks <PR#> --watch` to monitor. Use the
    `mcp__contextstream__session(action="capture_lesson", ...)` to record
    any false-positive bot patterns we discover.
  codex: |
    Use `gh pr checks <PR#> --watch` to monitor. Record false-positive bot
    patterns in `.ai-context/lessons.md` (committed snapshot fallback).
---

# PR Checks Completion Gate

Body shared between targets. The body_overrides above replace specific
sub-sections — the matching is by section heading.
```

Override matching strategy: each override is a markdown fragment; the parser scans the body for the same headings and replaces them on emit. If a heading from the override doesn't exist in the body, that's a hard validation error (V11) — overrides cannot introduce sections, only replace them. This keeps the body the source of truth for structure.

## CI integration per target

Each emitter participates in two CLI flows:

- `dotnet ai-config emit` — writes files into the repo working tree.
- `dotnet ai-config check` — runs emitters in dry-run mode and compares against the in-tree files. Failure conditions:
  - File missing
  - File present but content differs
  - Extra file in tree under a generator-managed path
  - Diagnostics emitted with severity ≥ warning when `--strict`

The CI workflow template emits a single composite check status per repo. Per-target check failures appear as separate annotations (e.g. "Cursor target out of date in `.cursor/rules/commits.mdc`").
